# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This repo hosts the `html-planning` Claude Code skill — not a project that consumes it. The skill itself lives in `skills/html-planning/` (the **Vercel skills package layout**: the skill folder is a discovered `skills/<name>/SKILL.md` subfolder), and the repo root is a normal Node project. Editing files under `skills/html-planning/` changes the skill's behavior for every repo that installs it (via symlink or copy into `.claude/skills/<name>/` — any folder name works; see the runtime-load contract below). The runtime files are served as-is to the browser.

Everything at the repo **root** (`package.json`, `tests/`, `node_modules/`) is a sibling of the skill folder — it is never discovered and never installed, so dev tooling is "tree-shaken" out of the delivered artifact by construction.

`skills/html-planning/SKILL.md` is the agent-facing contract (loaded into Claude's context when the skill is invoked). `README.md` at the repo root is the human-facing version. Both document the same component vocabulary — keep them in sync with the code.

`skills/html-planning/references/` holds deep-dive docs that SKILL.md **points at rather than inlines** — currently `template-authoring.md`. The split is by audience: SKILL.md covers *using* the skill and is paid for on every invocation, so guidance only a template author needs belongs in a reference, read on demand. Note this directory must live **inside** the skill folder: anything at the repo root is never installed, so a root-level `references/` would leave the pointer dangling for everyone who installs the skill. When adding a reference, link it from SKILL.md at the point of need — an unlinked reference is never read.

## Verifying changes

The repo is a Node project (root `package.json`, vitest the only dev dependency). Run the tests with:
```bash
npm install
npm test        # vitest run — unit + integration suites
```
`tests/planr.unit.test.js` imports the pure engine directly (`planr.js` is import-safe: `module.exports` + `if (require.main === module) main()`), and `tests/planr.cli.test.js` drives the CLI as a subprocess (dispatch, exit codes, stderr, stdin, round-trips). `tests/helpers.js` reaches `planr.js` through a single `PLANR` path constant.

To verify a change to `plan-runtime.js` or `plan-styles.css`, open `skills/html-planning/examples/sample-plan.html` in a browser — it exercises every component. The sample plan loads its assets via the same inline loader as a real plan, so it only renders correctly when opened from a path where the loader can resolve the skill folder (it falls back to `.claude/skills/html-planning` relative to the page). When adding or changing a component, **add a demonstrating instance to `skills/html-planning/examples/sample-plan.html`** so the showcase stays complete.

Generate a fresh skeleton to test `planr`:
```bash
node skills/html-planning/planr.js new /tmp/test-plan.html --title "Test" --template tdd
```

## Architecture: the runtime-load contract

A generated plan file contains **only semantic `<plan-*>` markup** — no inline CSS or JS. All styling and behavior arrives at runtime. The mechanism:

1. `planr new` composes a plan from `templates/_shell.html` (the shared document whose `<head>` contains the **inline loader** — the one piece of JS that must live in the plan file) and a body template, filling `{{title}}`/`{{date}}`/`{{skillSubpath}}`/`{{body}}` via a zero-dep `{{var}}` substitution. The loader walks `location.pathname`, finds the `.claude` segment, and resolves `{plan-styles.css, plan-runtime.js}` from there. The skill's install subpath (e.g. `skills/html-planning`) is **baked into the loader at generation time** — `planr` derives it from `process.argv[1]` (its own invocation path, which preserves the symlinked `.claude/skills/<name>/` even though `__dirname` would resolve through the link to the source repo). This is why the skill **no longer needs a fixed folder name**: install it under any name within `.claude/skills/` and the generated plans point at it. If `planr` is run from a path with no `.claude` segment (e.g. editing the skill itself), it falls back to `skills/<its-own-folder-name>`. (Template *bodies* are read relative to `planr.js`'s own dir, so they resolve through the symlink to the source repo.)
2. `plan-styles.css` is the dark, GitHub-inspired design system (CSS custom properties in `:root`, then component classes).
3. `plan-runtime.js` defines a Web Component class per `<plan-*>` tag. Each `connectedCallback` reads attributes + existing `innerHTML` and rewrites `innerHTML` into styled markup that targets the CSS classes.

`file://`-opened plans are fully interactive but **cannot read source files** (browsers block `fetch()` of local files). Live source reads and exact git diffs are the job of **Mimir**, a separate companion desktop app — not this skill.

## The planr command layering (core / shell / die)

`planr.js` is split into three layers, and new commands must follow the same shape:

1. **Pure `plan*` cores** — one per command (`planNew`, `planList`, `planCheck`, `planTasks`, `planRead`, `planTemplates`, `planSet`, `planSetBody`, `planInsert`, `planBadge`, `planAddSection`, `planRmSection`, `planMoveSection`). A core takes plan text (and args) and **returns** a value — a string for read-only commands, `{ html, message }` for mutators, `{ ok, report }` for `check` — and **throws `PlanError`** on any expected, user-facing failure. Cores never touch `fs` or `process`, so their logic *and every error path* are unit-testable in-process (`tests/planr.cores.test.js`, via `toThrow` / return values). A body is always **passed in** as a string; the core never reads it from disk — `planNew` likewise takes the shell and body **templates** as strings, so the whole generator is testable without a `templates/` dir.
2. **Thin `cmd*` IO shells** — read the file (and stdin/`--body-file`), call the core, then `write`/print. The shell is the only IO boundary; it holds no validation text.
3. **`main()` is the sole `die()` site.** It wraps dispatch in `try { … } catch (e) { if (e instanceof PlanError) die(e.message); throw e; }`, so a `PlanError` becomes `planr: <msg>\n` on stderr + exit 1, and any non-`PlanError` surfaces as a raw stack (a real bug, not a tidy user error). **Never** call `die()` / `process.exit()` anywhere else — a core that exits re-breaks unit-testability.

When adding a command: write the pure `plan*` core (throwing `PlanError`), add a thin `cmd*` shell, wire it into `main()`'s dispatch + `NEEDS_FILE`, export the core from `module.exports`, document it in `SKILL.md`'s command-reference table **and** the `USAGE` string, and cover it in `tests/planr.cores.test.js` (happy + error). Keep the integration suite (`tests/planr.cli.test.js`) to wiring only — dispatch, exit codes, stdin, round-trips, the `.claude` subpath bake, and at least one error→exit-1 case that proves `main()`'s catch fires. Low-level helpers (`walkTags`, `fitBlock`, `ownElements`, `resolveContainer`) belong in `tests/planr.unit.test.js` alongside the scanner.

### Invariants a new command must not break

- **One address grammar.** Every address argument — the positional one, `--parent`, `--after`, `--before`, `--in`, and a **dotted** `new --set` key — is a dot-path resolved by `resolveNode`. Never add a flag that takes a bare sibling id or any other second grammar; that was a real bug (`add-section` took relative refs while `move-section` took full paths, and `SKILL.md` documented only the latter). `new --set` is the same lesson from the other side: it used to take template-placeholder keys while `set` took addresses, sharing a flag name and `k=v` syntax with nothing marking the difference, so `--set header.status=review` — the obvious first guess — was written into the var map and never read. A dotted key now routes through `planSet` on the rendered file, which is why `new` gets that validation for free. **`--into <sel>` is the single sanctioned exception**, and only because it addresses something the dot-path deliberately cannot reach: a plain HTML container (`ul`, `tbody`, `#id`) *inside* an already-addressed section. It never accepts a `<plan-*>` tag. Read flag values with `flagValue(flags, key)`, which normalises the absent / valueless / repeated cases.
- **A valueless flag must be declared in `BOOLEAN_FLAGS`.** `parseFlags` otherwise consumes the next token as the flag's value, so `tasks --all plan.html` ate the filename and then reported a missing `<file>` with the file right there on the line. Adding a boolean flag means adding it to that set, or flag order silently matters.
- **Nothing is dropped in silence.** An argument the CLI accepts must take effect or throw. `set` reading only `positional[1]` and `new --set` swallowing unmatched keys were the same defect twice, both exiting 0 while printing a success line. When adding a command, ask what happens to a *second* value, an unknown key, and an ambiguous match — the answer is never "ignore it".
- **Status enums are per-tag, and paired with CSS.** `statusEnum(tag)` picks `HEADER_STATUS` or `SECTION_STATUS`; validating only sections let a typo'd header status through. Every `HEADER_STATUS` value needs a matching `.dot.<value>` rule in `plan-styles.css` (a test asserts the two sets are equal), and every `BADGE_TYPES` value a `plan-badge[type="…"]` rule. Adding a value means touching both files.
- **`check` reads through `walkTags`, not `findElement`.** `findElement`/`findClose` return `null` on the unbalanced markup `check` exists to report, so `check` uses the linear `walkTags` scan and a tag stack. Keep `PLAN_TAGS` in step with `plan-runtime.js`'s `components` map, or a valid component gets reported as unregistered. `BALANCED_HTML_TAGS` must contain only tags whose end tag is never optional in HTML — adding `p` or `li` would false-positive on legal markup.
- **`set-body` is verbatim, hunk inserts are fitted.** `planSetBody` must stay byte-exact (the `read --body | set-body` round-trip test depends on it). `planInsert` deliberately does *not*: it drops blank edge lines and applies the anchor's indentation via `fitBlock`, but only when the hunk has none of its own. Don't unify them.
- **`sectionIds` is shallow; `allSectionIds` is deep.** The shallow one exists for `assertIntact`, which must catch an accidental document collapse but must NOT fire when `set-body` legitimately replaces a parent's nested children. Uniqueness checks use the deep one. Picking the wrong one silently either false-positives on every `set-body` or lets duplicate ids through.
- **The settable surface belongs to the template, not to `planr.js`.** `render` honours `{{name:default}}`, so an author makes an attribute configurable by writing it as a placeholder — never by adding a name to a list in the code. `templateVars` returns `{name, def}` for each, which drives both the `--set` error message and the `templates <name>` listing, so a var cannot be settable-but-undocumented. Note the shell and the body are **both** scanned: `lang` and the header attributes live in `_shell.html`, and reporting the body alone is how they went undocumented. A placeholder with no declared default is left intact when unset, so a missing required var is visible in the output.
- **A bare `--set` fill bypasses `planSet`, so `planNew` re-validates the rendered header.** Any future validation that `set` applies to an attribute must be mirrored there, or the placeholder path becomes the hole the node path closed.
- **A template's leading comment is its documentation.** `templateDoc` extracts it and `templateSummary` reduces it to a first sentence, so `planr templates` can list every template with a gist and `planr templates <name>` can print the whole thing. Adding a template means opening it with that comment. Two constraints the extractor depends on: the comment must come **before any element** (anything later is an ordinary inline comment), and it must contain **no literal `<plan-*>` tag** — a test asserts both for every shipped template, because such a tag inflates a reader's `grep -c` count in the balanced way that never looks like a failure.
- **Numbers are derived, never stored.** `sectionNumber()` mirrors `_sectionNumber()` in `plan-runtime.js`; if you change one, change both, or the CLI and the rendered page will disagree. Templates must not hardcode `num` — an inserted section would collide with the frozen numbers.
- **Attribute values are HTML-escaped on disk.** Anything printed to a terminal goes through `decodeEntities` first, or a title reads `Scope &amp; Prerequisites`.

## Adding or changing a component

A component spans **four** places that must stay aligned:

1. **`plan-runtime.js`** — define the `HTMLElement` subclass and add it to the `components` map at the bottom (the map drives `customElements.define`).
2. **`plan-styles.css`** — add the classes the component's `innerHTML` references.
3. **`SKILL.md`** — document the tag, its attributes, and an example. This is what future Claude instances actually read; an undocumented component effectively does not exist.
4. **`skills/html-planning/examples/sample-plan.html`** — add a live instance.

`README.md`'s component list is a summary — update it when the set of components changes, but the per-attribute detail lives in `SKILL.md`.

### Runtime conventions to match

- **Ordering / timing:** components that need their children or sibling sections present (`plan-nav`, `plan-tabs`) defer work to `requestAnimationFrame`. highlight.js runs `hljs.highlightAll()` one frame after registration so components finish rewriting their `innerHTML` first. Preserve this ordering when touching anything that highlights code.
- **Per-line rows:** both `plan-file` and `plan-diff` render each source line as its own `[gutter][text]` flex row, wrapped in a `.file-inner`/`.diff-inner` element sized `min-width: 100%; width: max-content`. This keeps gutter numbers aligned with their code even when lines soft-wrap, and lets the add/del backgrounds span the full width on horizontal scroll. Because lines are highlighted individually (`hljs.highlight(line, …)`), neither component participates in `hljs.highlightAll()` — don't expect cross-line highlight context.
- **Escaping:** code-bearing components (`plan-file`, `plan-diff`) read `this.textContent` raw (via `_trimEdgeBlankLines`, which strips blank edge lines **without** touching the first content line's indentation — never use plain `.trim()` here), then escape via `_escapeHtml` before injecting. Attribute values are interpolated directly into `innerHTML` and are **not** escaped — they're authored by Claude, not untrusted input, so don't add escaping that would break intentional markup, but don't introduce a path where untrusted text reaches an attribute either.
- **Language detection:** `plan-file`/`plan-diff` map file extension → highlight.js language via `_extLangMap`. Extend that map rather than special-casing.
- **Numeric attributes:** `plan-file`'s `lines` is treated as a range only when it parses to a real integer (otherwise the gutter starts at 1). Keep this "parse-or-ignore" behavior for any new numeric attribute.
- **View settings (gear):** `_initPlanSettings()` (bottom of `plan-runtime.js`) injects a fixed top-right gear + popover with runtime view preferences, persisted to `localStorage` under `plan-view-settings`. `PLAN_SETTINGS` is an array of **groups** (`{title, settings: [{key, label, default, apply}]}`) rendered as titled buckets (`View`, `Navigation`); `apply` toggles a class on `<html>` that CSS keys off (e.g. `wrap` → `.plan-wrap`, `sidebar` → `.plan-sidebar`), or acts on the tree directly (`navCollapsed` toggles `.collapsed` on every `.plan-tree li.has-children`). Add a setting by pushing an entry into a group's `settings` (plus matching CSS); add a bucket by pushing a group. **Read every setting through `_viewSetting(key)`, never `_readView()[key]`** — `_viewSetting` falls back to the entry's `default` when the reader has no stored choice, and only the toggled key is written back, so an untouched setting keeps tracking its default instead of freezing the value it happened to have. `sidebar` defaults to `true` (the side-panel tree is the primary navigation; `plan-nav`'s top bar is the fallback view), which is also why `plan-nav`'s scroll-spy threshold falls back to a fixed `120` when its `offsetHeight` is 0. The gear is vertically centered against `plan-nav`'s measured height via a `ResizeObserver` (nav has no fixed height and populates a frame late), falling back to its CSS `top` when no nav is present.
- **Nav tree collapse:** the side-panel tree (`_initPlanTree`) gives every row with children a right-aligned `.tree-caret` button that toggles `.collapsed` on its `<li>` (CSS hides the child `<ul>` and rotates the caret). Initial state honors the `navCollapsed` setting; per-item toggles are ephemeral (not persisted). This is distinct from the whole-panel `.tree-collapsed` toggle in the header.
- **Lazy external libraries:** highlight.js is loaded eagerly by the generator skeleton, but `plan-diagram` lazy-loads **Mermaid from cdnjs at runtime** — `_ensureMermaid()` injects the UMD `mermaid.min.js` only the first time a `<plan-diagram>` connects, caches the load promise, and initialises it with `theme: 'base'` + `themeVariables` read from the plan's own CSS custom properties (so diagrams match the palette). This is the pattern for any future heavy/optional dependency: keep it out of the skeleton templates (backwards compat + lean skeletons) and lazy-inject it from the component that needs it, gated on that component's presence. Diagrams render via `mermaid.render(id, src)`; parse/load failures fall back to showing the raw source.

## The core authoring rules (enforced by SKILL.md)

When generating plans (not editing the skill itself), the non-negotiable rules are: always run `planr new` first; never write inline `<style>`/`<script>`/CSS-custom-properties in a plan file; never hand-roll `<div>` structures where a `<plan-*>` component exists; encode code changes as `<plan-diff>`/`<plan-file>` rather than prose ("around line 45, change X"). If you change these rules, change them in `SKILL.md` — that text is the source of truth agents load.
