# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This repo hosts the `html-planning` Claude Code skill — not a project that consumes it. The skill itself lives in `skills/html-planning/` (the **Vercel skills package layout**: the skill folder is a discovered `skills/<name>/SKILL.md` subfolder), and the repo root is a normal Node project. Editing files under `skills/html-planning/` changes the skill's behavior for every repo that installs it (via symlink or copy into `.claude/skills/<name>/` — any folder name works; see the runtime-load contract below). The runtime files are served as-is to the browser.

Everything at the repo **root** (`package.json`, `tests/`, `node_modules/`) is a sibling of the skill folder — it is never discovered and never installed, so dev tooling is "tree-shaken" out of the delivered artifact by construction.

`skills/html-planning/SKILL.md` is the agent-facing contract (loaded into Claude's context when the skill is invoked). `README.md` at the repo root is the human-facing version. Both document the same component vocabulary — keep them in sync with the code.

`skills/html-planning/references/` holds deep-dive docs that SKILL.md **points at rather than inlines** — `template-authoring.md` and `authoring-traps.md`. The split is by audience: SKILL.md covers *using* the skill and is paid for on every invocation, so guidance only a template author needs belongs in a reference, read on demand. Note this directory must live **inside** the skill folder: anything at the repo root is never installed, so a root-level `references/` would leave the pointer dangling for everyone who installs the skill. When adding a reference, link it from SKILL.md at the point of need — an unlinked reference is never read.

## Verifying changes

The repo is a Node project (root `package.json`, vitest the only dev dependency). Run the tests with:
```bash
npm install
npm test        # vitest run — unit + integration suites
```
`tests/planr.unit.test.js` imports the pure engine directly (`planr.js` is import-safe: `module.exports` + `if (require.main === module) main()`), and `tests/planr.cli.test.js` drives the CLI as a subprocess (dispatch, exit codes, stderr, stdin, round-trips). `tests/helpers.js` reaches `planr.js` through a single `PLANR` path constant.

**Any change to `plan-runtime.js` or `plan-styles.css` must pass `npm run verify:runtime`.** It loads `skills/html-planning/examples/sample-plan.html` in a headless browser twice — over `file://`, and through `tests/runtime/serve-split.mjs`, which pauses the HTML just inside the first `<plan-diagram>` — and runs the assertions in `tests/runtime/verify-diagrams.mjs` on a cold load, three warm reloads, a DOM move and an empty diagram, then on the tone colours of the status dot and every badge type, and on the header's metadata chips (toned, hidden, repeated-key and legacy-chip cases injected into the live page). Opening the sample over `file://` is **not** sufficient: the runtime loads from disk before the parser reaches the components, so the parse race never occurs and a broken registration passes. The harness needs the browser-automation driver (`~/.claude/skills/browser-automation/browser.mjs`, or `BROWSER_MJS`) and network access for Mermaid, which is why it is kept out of `npm test`. The sample plan's inline loader resolves assets from its own path (`<skill>/examples/..`), so it renders straight from this repo. When adding or changing a component, **add a demonstrating instance to `skills/html-planning/examples/sample-plan.html`** so the showcase stays complete.

Generate a fresh skeleton to test `planr`:
```bash
node skills/html-planning/planr.js new /tmp/test-plan.html --title "Test" --template tdd
```

## Architecture: the runtime-load contract

A generated plan file contains **only semantic `<plan-*>` markup** — no inline CSS or JS. All styling and behavior arrives at runtime. The mechanism:

1. `planr new` composes a plan from `templates/_shell.html` (the shared document whose `<head>` contains the **inline loader** — the one piece of JS that must live in the plan file) and a body template, filling `{{title}}`/`{{date}}`/`{{skillSubpath}}`/`{{body}}` via a zero-dep `{{var}}` substitution. The loader walks `location.pathname`, finds the `.claude` segment, and resolves `{plan-styles.css, plan-runtime.js}` from there. The skill's install subpath (e.g. `skills/html-planning`) is **baked into the loader at generation time** — `planr` derives it from `process.argv[1]` (its own invocation path, which preserves the symlinked `.claude/skills/<name>/` even though `__dirname` would resolve through the link to the source repo). This is why the skill **no longer needs a fixed folder name**: install it under any name within `.claude/skills/` and the generated plans point at it. If `planr` is run from a path with no `.claude` segment (e.g. editing the skill itself), it falls back to `skills/<its-own-folder-name>`. (Template *bodies* are read relative to `planr.js`'s own dir, so they resolve through the symlink to the source repo — plus from the consumer directory `.claude/planr-templates/`, which `resolveConsumerTemplateDir` derives from the same `argv[1]` `.claude` segment. `loadTemplates` merges the two through the pure `planTemplateIndex`: a consumer template shadows a skill one of the same name, and a consumer `_shell.html` throws.)
2. `plan-styles.css` is the dark, GitHub-inspired design system (CSS custom properties in `:root`, then component classes).
3. `plan-runtime.js` defines a Web Component class per `<plan-*>` tag. Each `connectedCallback` reads attributes + existing `innerHTML` and rewrites `innerHTML` into styled markup that targets the CSS classes.

`file://`-opened plans are fully interactive but **cannot read source files** (browsers block `fetch()` of local files). Live source reads and exact git diffs are the job of **Mimir**, a separate companion desktop app — not this skill.

## The planr command layering (core / shell / die)

`planr.js` is split into three layers, and new commands must follow the same shape:

1. **Pure `plan*` cores** — one per command (`planNew`, `planList`, `planCheck`, `planTasks`, `planRead`, `planTemplates`, `planSet`, `planSetBody`, `planInsert`, `planBadge`, `planRmItem`, `planStrike`, `planReplace`, `planAddSection`, `planRmSection`, `planMoveSection`). A core takes plan text (and args) and **returns** a value — a string for read-only commands, `{ html, message }` for mutators, `{ ok, report, warnings }` for `check` — and **throws `PlanError`** on any expected, user-facing failure. Cores never touch `fs` or `process`, so their logic *and every error path* are unit-testable in-process (`tests/planr.cores.test.js`, via `toThrow` / return values). A body is always **passed in** as a string; the core never reads it from disk — `planNew` likewise takes the shell and body **templates** as strings, so the whole generator is testable without a `templates/` dir.
2. **Thin `cmd*` IO shells** — read the file (and stdin/`--body-file`), call the core, then `write`/print. The shell is the only IO boundary; it holds no validation text.
3. **`main()` is the sole `die()` site.** It wraps dispatch in `try { … } catch (e) { if (e instanceof PlanError) die(e.message); throw e; }`, so a `PlanError` becomes `planr: <msg>\n` on stderr + exit 1, and any non-`PlanError` surfaces as a raw stack (a real bug, not a tidy user error). **Never** call `die()` / `process.exit()` anywhere else — a core that exits re-breaks unit-testability.

When adding a command: write the pure `plan*` core (throwing `PlanError`), add a thin `cmd*` shell, wire it into `main()`'s dispatch + `NEEDS_FILE`, export the core from `module.exports`, document it in `SKILL.md`'s command-reference table **and** the `USAGE` string, and cover it in `tests/planr.cores.test.js` (happy + error). Keep the integration suite (`tests/planr.cli.test.js`) to wiring only — dispatch, exit codes, stdin, round-trips, the `.claude` subpath bake, and at least one error→exit-1 case that proves `main()`'s catch fires. Low-level helpers (`walkTags`, `walkNodes`, `visibleUnits`, `fitBlock`, `ownElements`, `resolveContainer`) belong in `tests/planr.unit.test.js` alongside the scanner.

### Invariants a new command must not break

- **One address grammar.** Every address argument — the positional one, `--parent`, `--after`, `--before`, `--in`, and a **dotted** `new --set` key — is a dot-path resolved by `resolveNode`. Never add a flag that takes a bare sibling id or any other second grammar; that was a real bug (`add-section` took relative refs while `move-section` took full paths, and `SKILL.md` documented only the latter). `new --set` is the same lesson from the other side: it used to take template-placeholder keys while `set` took addresses, sharing a flag name and `k=v` syntax with nothing marking the difference, so `--set header.status=review` — the obvious first guess — was written into the var map and never read. A dotted key now routes through `planSet` on the rendered file, which is why `new` gets that validation for free. **`--into <sel>` is the single sanctioned exception**, and only because it addresses something the dot-path deliberately cannot reach: a container (`ul`, `tbody`, `#id`, or a component such as `plan-defs` or `plan-cards`) *inside* an already-addressed section. It refuses exactly the tags the dot-path addresses — `plan-section`, `plan-subsection`, `plan-header` (`DOT_PATH_TAGS`) — as a property of the grammar, not an allow-list: whatever the dot-path reaches is addressed by it, and everything else can only be reached by `--into`. Read flag values with `flagValue(flags, key)`, which normalises the absent / valueless / repeated cases.
- **Every flag a command reads is declared in `COMMAND_FLAGS`, with its kind.** Each entry is `'bool'` (never takes a value) or `'value'`; `isBooleanFlag` reads the kind from the table, so `parseFlags` never consumes the next token for a `'bool'` flag — `tasks --all plan.html` once ate the filename that way. The kind is per command (`read --text` is `'bool'`, `badge --text <T>` is `'value'`); never add a global flag set or a per-command exception beside the table. `main()` refuses any undeclared flag through `assertKnownFlags` before dispatch, so a flag nothing reads is an error rather than a silent no-op (`list --outline` was one for releases). A core test holds `COMMAND_FLAGS` and the `USAGE` lines to the same flags in both directions. Adding a flag means one `COMMAND_FLAGS` entry and a `USAGE` mention; `--help` is the one flag every command accepts.
- **Nothing is dropped in silence.** An argument the CLI accepts must take effect or throw. `set` reading only `positional[1]` and `new --set` swallowing unmatched keys were the same defect twice, both exiting 0 while printing a success line. When adding a command, ask what happens to a *second* value, an unknown key, and an ambiguous match — the answer is never "ignore it".
- **Status enums are per-tag; every colour is a tone.** `statusEnum(tag)` picks `HEADER_STATUS` or `SECTION_STATUS`; validating only sections let a typo'd header status through. `TONES` is the one colour vocabulary: each tone has a `.dot.tone-<t>` and a `plan-badge.tone-<t>` rule in `plan-styles.css` (a test asserts both sets equal `TONES`). `HEADER_STATUS` is `Object.keys(HEADER_STATUS_TONES)`, which must equal `STATUS_TONES` in `plan-runtime.js`; `BADGE_TYPES` is `Object.keys(BADGE_LABELS)`, and `BADGE_LABELS` and `BADGE_TONES` must equal `PlanBadge`'s `labels` and `tones` maps (tests assert all three). `badge --set` and `check` read the planr copies. Adding a status or a badge type means giving it a tone in both files; adding a tone means two CSS rules. Never write a per-type or per-status colour rule.
- **`check` reads through `walkTags`, not `findElement`.** `findElement`/`findClose` return `null` on the unbalanced markup `check` exists to report, so `check` uses the linear `walkTags` scan and a tag stack. Keep `PLAN_TAGS` in step with `plan-runtime.js`'s `components` map, or a valid component gets reported as unregistered — a core test parses the map and asserts the two tag sets are equal. `BALANCED_HTML_TAGS` must contain only tags whose end tag is never optional in HTML — adding `p` or `li` would false-positive on legal markup. **Parent legality is two tables, not a second scan rule:** `LEGAL_PARENTS` (where each table tag may open) and `INLINE_HOSTS` (the phrasing elements no block may open inside; its `plan-*` members are read from `TEXT_RULES`, never listed) drive `nestingProblems`, whose block set is derived from `TEXT_RULES`, so a new block component is covered with no edit there. It tracks `td`/`th` and the inline hosts *softly* — never balance-checked, dropped when their parent closes — which is why they stay out of `BALANCED_HTML_TAGS`. `checkStructure` runs it only once the tags balance; `planReplace` runs it on its own splice, so a document already failing `check` still refuses a new misnesting. The warning tier is the one exception, and it is scoped: `planCheck` runs `lintPlan` only after `checkStructure` passes, so the lints may locate elements with `findElement`. `assertIntact` gates every write on `checkStructure` alone — a warning must never block a write.
- **A component registered in `PLAN_TAGS` declares its `read --text` rule.** `TEXT_RULES` says whether the tag is `block`, `inline` or `code` and which of its attributes print, and a core test asserts every `PLAN_TAGS` entry has one. Content that lives only in an attribute (a card's `value`, a diagram's `caption`) is otherwise dropped from `read --text`, and a tag without a rule reads as inline, which changes how `rm-item`/`strike`/`replace` match across it. `visibleUnits` is the one tag-to-text rule; never add a second (`textOf` stays for `badge` and `insert` only).
- **`set-body` is verbatim, hunk inserts are fitted.** `planSetBody` must stay byte-exact (the `read --body | set-body` round-trip test depends on it). `planInsert` deliberately does *not*: it drops blank edge lines and applies the anchor's indentation via `fitBlock`, but only when the hunk has none of its own. Don't unify them.
- **`sectionIds` is shallow; `allSectionIds` is deep.** The shallow one exists for `assertIntact`, which must catch an accidental document collapse but must NOT fire when `set-body` legitimately replaces a parent's nested children. Uniqueness checks use the deep one. Picking the wrong one silently either false-positives on every `set-body` or lets duplicate ids through.
- **The settable surface belongs to the template, not to `planr.js`.** `render` honours `{{name:default}}`, so an author makes an attribute configurable by writing it as a placeholder — never by adding a name to a list in the code. `templateVars` returns `{name, def}` for each, which drives both the `--set` error message and the `templates <name>` listing, so a var cannot be settable-but-undocumented. Note the shell and the body are **both** scanned: `lang` and the header attributes live in `_shell.html`, and reporting the body alone is how they went undocumented. A placeholder with no declared default is left intact when unset, so a missing required var is visible in the output.
- **Every attribute writer calls `validateAttr`; a new attribute rule is one table entry.** `planSet` calls it per assignment, `buildSection` per field, and `planNew` over the rendered header and sections (`validateNodes`), because a placeholder fill never passes through `planSet`. Never hand-place an attribute check in a single writer.
- **A template's leading comment is its documentation.** `templateDoc` extracts it and `templateSummary` reduces it to a first sentence, so `planr templates` can list every template with a gist and `planr templates <name>` can print the whole thing. `planNew` strips the same comment from the document it writes (`stripTemplateDoc`, using `templateDoc`'s own regex), so a scaffold never opens with instructions to itself. Adding a template means opening it with that comment. Two constraints the extractor depends on: the comment must come **before any element** (anything later is an ordinary inline comment), and it must contain **no literal `<plan-*>` tag** — a test asserts both for every shipped template, because such a tag inflates a reader's `grep -c` count in the balanced way that never looks like a failure. `templateProblems` is the runtime form of these rules plus "scaffolds to a plan that passes `check`": `planr templates` reports any template — shipped or consumer — that breaks one, and the core suite asserts every shipped template has none. A new template rule goes into `templateProblems`, not only into a test.
- **Numbers are derived, never stored.** `sectionNumber()` mirrors `_sectionNumber()` in `plan-runtime.js`; if you change one, change both, or the CLI and the rendered page will disagree. Templates must not hardcode `num` — an inserted section would collide with the frozen numbers.
- **Attribute values are HTML-escaped on disk.** Anything printed to a terminal goes through `decodeEntities` first, or a title reads `Scope &amp; Prerequisites`.
- **The metadata schema is data, not code.** `planr-schema.json` beside `planr.js` is the shipped core; a consuming repo's is `.claude/planr-schema.json`, found through the same `claudeRoot` derivation as `planr-templates/`. No field name, enum value or ranking name appears in `planr.js`. Adding a field means editing the JSON, never the JS. The core stays minimal — `type` is `issue`/`tdd`, `infer` and `defaults` are empty — because a document type or path rule one repo needs is another repo's noise. The two names `planr.js` does own are the built-in columns `path` and `blocked` (`BUILTIN_COLUMNS`), which no schema field may take, and `CLOSED_STATUS` is a subset of the header's own status enum, not schema data.
- **Schema validation is two passes, and only the second one sees the merge.** `parseSchema` checks shape per file and tags every part with its `origin`; `validateSchemaRefs`, which `mergeSchemas` always calls, checks cross-references on the merged result — because a consumer's `defaults` may legitimately name a core field. Both refuse loudly: a malformed schema is a `PlanError` naming the file, never an ignored key.
- **`validateField` is the ONE field-value rule.** Every writer of a `<plan-field>` value calls it — `planMetaSet`, `validateNodes` (so a template's declared defaults are held to the same rules as a `meta --set`) and `lintMeta`. It returns problem text rather than throwing, so the throwing callers and the collecting one share one rule. The `key` ATTRIBUTE still goes through `validateAttr`; the value is element content, which `ATTR_RULES` cannot address.
- **The page is schema-free; the writer stamps.** The runtime cannot read the schema, so `fieldStamp(schema, key, raw)` → `{ tone, hidden, label }` is the ONE stamping rule: `planMetaSet` stamps every field of the block it rebuilds, `planNew` stamps a template's declared fields through `stampMetaFields`, `planMetaStamp` (`meta --stamp`) rewrites only drifting `label`/`tone`/`hidden` attributes (`STAMP_ATTRS`), judged by `stampDrift`, never a value, and `lintMeta` reports any disagreement through `stampDrift`. `PlanHeader` renders `<plan-meta>`'s fields from those attributes alone — the chip shows the stamped `label`, falling back to the key — never teach the runtime a field name or a schema value. `label`, `tones` and `hidden` are shape-checked in `parseSchema`, since they read only the field's own def. A new rendering key is one more `fieldStamp` member and one more `STAMP_ATTRS` entry, never a second rule.
- **`resolveMeta`'s record is a consumed contract, not an internal shape.** `{ path, fields: { <name>: { value, raw, source, type, rank } }, unknown, problems }` — every schema field present, in schema-declaration order, and `rank` carrying the total order (enum index, the number, the ISO date, the lower-cased string, or null). `planr meta --format json` emits it verbatim and the query commands sort on `rank` alone. Changing a key changes an output format. `queryDocs` adds `derived` to each result it returns — `{ blocked }` in the same per-field shape plus `blockers`, or `{}` — and `resolveMeta` itself stays per-document and filesystem-free.
- **`<plan-meta>` is the FIRST element inside `<main>`.** `meta --set` creates it there, `check` warns when it is anywhere else, and a template declares its defaults by writing the block at the top of its body — which is why the position is inside `<main>` rather than beside the header: a template body can reach nowhere else.
- **One writable home per fact.** A schema field declared `from: "header:<attr>"` — `title`, `status`, `date` — is a READ-ONLY VIEW of the header attribute, and `headerOwnedProblem` is the one rule that says so. `planMetaSet` refuses a `--set` of one and names the real writer (`planr set <file> header.status=…`), `validateNodes` refuses a template that declares one, and `lintMeta` warns when a document already carries one. `resolveMeta` is deliberately unaffected: the C1 order stands, so there is exactly one resolution chain. The writers of those three values remain `planSet`, `planNew`'s dotted `--set` and `_shell.html`; a second copy in `<plan-meta>` would outrank the header and diverge the first time `planr set header.status=…` runs.
- **A metadata problem is a warning, never a structure failure.** `lintMeta` runs in `lintPlan`, so it can never block a write; `check --strict` is the gate. An empty field value is never valid: `--set k=` is refused, a template placeholder left empty is pruned by `new`, and an empty one in a document is a warning.
- **A condition has ONE shape and ONE evaluator.** A schema ranking's `where` and the CLI's `--where`/`--has`/`--missing`
  flags both produce `{ field: { op: literal } }`; `compileWhere` validates it and pre-ranks every literal; `matchWhere`
  reads only that compiled form and never sees the schema. The derived `blocked` column rides the same path:
  `conditionDef` is the one lookup that names it (for `parseWhere`, `compileWhere`, `parseSort` and `parseFields`), and
  `recField` the one read of it (for `matchWhere`, the sort and `cellText`). Never add a second place that interprets an operator — the
  two surfaces would agree the day they were written and diverge on the first operator either one gained. Compile the
  flag half and the ranking half **separately**, so a refusal names the origin the condition actually came from.
- **A ranking is validated by the code that runs it.** `validateSchemaRefs` calls `compileWhere` and `parseSort` on
  every ranking, so a ranking that LOADS is a ranking `query --rank` can execute. That is why an operator typo in a
  consumer schema fails `meta`, `check`, `new` and `templates` too: they all call `loadSchema()`.
- **`--fields` is a COLUMN list, never a record filter.** `query --format json`, `next --format json` and
  `meta --format json` all emit the same per-field record — every declared schema field present, `source: null` for an
  unset one. A key set that varied with the projection would make "not selected" and "no value" both read as
  `undefined` in a consumer.
- **`queryDocs` calls `checkStructure(html, { nesting: false })`, never `planCheck`.** It needs "does this balance", not
  the lints, and the lints are half the cost of a corpus scan. Nesting is off because a misnested element leaves
  `findElement` — and so every metadata read — intact, and a rendering defect must not hide a document from `next`.
  A metadata problem is `check`'s to report; `query` never opens a second channel for it.
- **Nothing a corpus scan cannot use is dropped in silence.** Unreadable, not-a-plan-document and does-not-balance each
  become a `skipped` entry, printed to stderr so stdout stays exactly the result set, carried in the JSON payload, and
  gated by `--strict`. A target that resolves to zero FILES is an error; a filter that matches zero documents is not.
- **`query` and `next` take a `<dir|glob>`, so they live in `NEEDS_TARGET`, not `NEEDS_FILE`.** Both of `main()`'s
  guards read those lists — the unknown-command check and the missing-argument check — and the second one prints
  "requires a `<file>` argument", which is false for a directory.
- **`next` is driven only by a named ranking.** There is no implicit order: a prioritisation policy in `planr.js` is a
  field vocabulary in `planr.js`, which the schema owns. An empty queue exits **0** — a caller polling "is there
  anything to do" must be able to tell nothing from broken.
- **A blocker resolves against its own document's directory, and a missing one never blocks.** `blockerPath` is the one
  resolution rule. `queryDocs` reads a target from the scanned `docs` or through the injected `readDoc`, once per run;
  `lintBlockers` takes the same `readDoc`, so "missing" is `readDoc(p) === null` for both — the cores take the filesystem as a function and never touch `fs`. A
  missing target is `check`'s to warn on; `query` never reports it. No git history is consulted.
- **No index, no cache.** `query` reads the documents. Measured on a 142-document, 8 MB corpus: ~230 ms wall clock,
  ~70 ms of which is Node's own startup. Re-measure before proposing one.

## Adding or changing a component

A component spans **four** places that must stay aligned:

1. **`plan-runtime.js`** — define the `HTMLElement` subclass and add it to the `components` map at the bottom (the map drives `customElements.define`).
2. **`plan-styles.css`** — add the classes the component's `innerHTML` references.
3. **`SKILL.md`** — document the tag, its attributes, and an example. This is what future Claude instances actually read; an undocumented component effectively does not exist.
4. **`skills/html-planning/examples/sample-plan.html`** — add a live instance.

`README.md`'s component list is a summary — update it when the set of components changes, but the per-attribute detail lives in `SKILL.md`.

### Runtime conventions to match

- **Registration waits for the parse:** the inline loader injects `plan-runtime.js` dynamically, so it runs async and can execute while `<body>` is still parsing. `_boot()` therefore defines the components on `DOMContentLoaded` (or at once, if parsing already finished). Defining them earlier upgrades an element whose children have not been appended yet, and every component that reads its own content in `connectedCallback` renders empty. Never move a `customElements.define` back to top level.
- **Ordering / timing:** components that need their children or sibling sections present (`plan-nav`, `plan-tabs`) defer work to `requestAnimationFrame`. highlight.js runs `hljs.highlightAll()` one frame after registration so components finish rewriting their `innerHTML` first. Preserve this ordering when touching anything that highlights code.
- **Per-line rows:** both `plan-file` and `plan-diff` render each source line as its own `[gutter][text]` flex row, wrapped in a `.file-inner`/`.diff-inner` element sized `min-width: 100%; width: max-content`. This keeps gutter numbers aligned with their code even when lines soft-wrap, and lets the add/del backgrounds span the full width on horizontal scroll. Because lines are highlighted individually (`hljs.highlight(line, …)`), neither component participates in `hljs.highlightAll()` — don't expect cross-line highlight context.
- **Diagram source:** `plan-diagram` is the one component that reads `this.innerHTML`, decoded by a **single-pass** `_decodeEntities`: `textContent` drops a label's `<br/>`, which the parser has already turned into an element. It stashes the result on `this._source` before overwriting `innerHTML`, so a re-connect re-renders from source, and it renders an explicit runtime-bug error for an empty source instead of passing `""` to Mermaid.
- **Escaping:** code-bearing components (`plan-file`, `plan-diff`) read `this.textContent` raw (via `_trimEdgeBlankLines`, which strips blank edge lines **without** touching the first content line's indentation — never use plain `.trim()` here), then escape via `_escapeHtml` before injecting. Attribute values are interpolated directly into `innerHTML` and are **not** escaped — they're authored by Claude, not untrusted input, so don't add escaping that would break intentional markup, but don't introduce a path where untrusted text reaches an attribute either.
- **Language detection:** `plan-file`/`plan-diff` map file extension → highlight.js language via `_extLangMap`. Extend that map rather than special-casing.
- **Numeric attributes:** `plan-file`'s `lines` is treated as a range only when it parses to a real integer (otherwise the gutter starts at 1). Keep this "parse-or-ignore" behavior for any new numeric attribute.
- **View settings (gear):** `_initPlanSettings()` (bottom of `plan-runtime.js`) injects a fixed top-right gear + popover with runtime view preferences, persisted to `localStorage` under `plan-view-settings`. `PLAN_SETTINGS` is an array of **groups** (`{title, settings: [{key, label, default, apply}]}`) rendered as titled buckets (`View`, `Navigation`); `apply` toggles a class on `<html>` that CSS keys off (e.g. `wrap` → `.plan-wrap`, `sidebar` → `.plan-sidebar`), or acts on the tree directly (`navCollapsed` toggles `.collapsed` on every `.plan-tree li.has-children`). Add a setting by pushing an entry into a group's `settings` (plus matching CSS); add a bucket by pushing a group. **Read every setting through `_viewSetting(key)`, never `_readView()[key]`** — `_viewSetting` falls back to the entry's `default` when the reader has no stored choice, and only the toggled key is written back, so an untouched setting keeps tracking its default instead of freezing the value it happened to have. `sidebar` defaults to `true` (the side-panel tree is the primary navigation; `plan-nav`'s top bar is the fallback view), which is also why `plan-nav`'s scroll-spy threshold falls back to a fixed `120` when its `offsetHeight` is 0. The gear is vertically centered against `plan-nav`'s measured height via a `ResizeObserver` (nav has no fixed height and populates a frame late), falling back to its CSS `top` when no nav is present.
- **Nav tree collapse:** the side-panel tree (`_initPlanTree`) gives every row with children a right-aligned `.tree-caret` button that toggles `.collapsed` on its `<li>` (CSS hides the child `<ul>` and rotates the caret). Initial state honors the `navCollapsed` setting; per-item toggles are ephemeral (not persisted). This is distinct from the whole-panel `.tree-collapsed` toggle in the header.
- **Lazy external libraries:** highlight.js is loaded eagerly by the generator skeleton, but `plan-diagram` lazy-loads **Mermaid from cdnjs at runtime** — `_ensureMermaid()` injects the UMD `mermaid.min.js` only the first time a `<plan-diagram>` connects, caches the load promise, and initialises it with `theme: 'base'` + `themeVariables` read from the plan's own CSS custom properties (so diagrams match the palette). This is the pattern for any future heavy/optional dependency: keep it out of the skeleton templates (backwards compat + lean skeletons) and lazy-inject it from the component that needs it, gated on that component's presence. Every diagram type is initialised with `useMaxWidth: false` (`_MERMAID_DIAGRAM_TYPES`), and `.diagram-render svg` carries `max-width: none`, so a wide diagram keeps its natural size and `.diagram-body` scrolls it. Diagrams render via `mermaid.render(id, src)`; parse/load failures fall back to showing the raw source.

## The core authoring rules (enforced by SKILL.md)

When generating plans (not editing the skill itself), the non-negotiable rules are: always run `planr new` first; never write inline `<style>`/`<script>`/CSS-custom-properties in a plan file; never hand-roll `<div>` structures where a `<plan-*>` component exists; encode code changes as `<plan-diff>`/`<plan-file>` rather than prose ("around line 45, change X"). If you change these rules, change them in `SKILL.md` — that text is the source of truth agents load.
